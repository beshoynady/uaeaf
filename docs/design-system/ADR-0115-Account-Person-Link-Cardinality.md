# ADR-0115 — One account, one person, and the link can be changed after creation

| Field | Details |
| --- | --- |
| **Status** | Accepted. Recorded 2026-09-26. Closes P1-3 and P2-1 in `docs/reviews/accounts-profiles-review.md`. |
| **Authority** | Product Owner brief, 2026-09-26 (decision F5), which resolves the earlier question 4 in favour of a link endpoint. |
| **Amends** | `users.personId` gains a partial unique index and a writer after creation. |
| **Does not amend** | Decision D1 — the account and the person stay separate entities with an **optional** link. An account with no person and a person with no account both remain valid. · D4 — locking an account still does not touch the person, and archiving a person still does not lock the account. |
| **Context** | `personId` is `nullable` with `default: null`, which correctly makes the link optional, and `resolvePersonId` verifies the person exists. Three things are missing. There is **no unique index** — the only index on `users` is the email one — so two accounts may point at the same person, which contradicts the one-to-one the decision states. The field is **write-once**: it is set in `create` and no route changes it, so an existing employee appointed to the board cannot have their account linked without deleting the account, which is itself impossible (no `users:Delete` exists). And **nothing reads it** — a grep finds two references, the write and the response mapper — so a dangling reference to an archived person would go unnoticed indefinitely. |
| **Decision** | A **partial unique index** on `personId` where `personId ≠ null` and `archivedAt: null`, preceded by a duplicate-check script that must report zero — the `check-policy-duplicates` precedent. A new `PATCH /users/:id/person` taking `{ personId \| null }`, subject to ADR-0104's stronger-user rule. **Archiving a person clears `personId` on any linked account**, so the dangling reference cannot form. |
| **Alternatives Considered** | **(A) Leave the link settable only at creation.** Rejected: the realistic case — an existing staff member is appointed to the board — has no path at all, because the account cannot be deleted and recreated. **(B) Put the writer on the person side** (`PATCH /federation-personnel/:id/user`). Rejected: it places a write to `users` inside the `federationPersonnel` permission scope, so someone who may edit a person could rebind accounts. **(C) A plain unique index rather than partial.** Rejected: it would treat many `null`s as duplicates and block every unlinked account after the first. **(D) Enforce uniqueness in the service only.** Rejected: two concurrent requests both pass a service check and both write. The index is the only thing that holds under concurrency. **(E) Leave the dangling reference and add an integrity report.** Rejected as the primary fix: the reference reads as `null` through the soft-delete-aware `findById` anyway, so it is silently wrong rather than visibly broken — clearing it at the source is cheaper than detecting it later. |
| **Why This Decision** | One-to-one was already the stated decision and was simply never enforced, so this adds the enforcement rather than a new idea. Doing the duplicate check before the index is not ceremony: an index build against existing duplicates fails, and the failure at deploy time is worse than the report beforehand. |
| **Risks** | **The index build fails on live data.** **Mitigation:** the check script runs first and must report zero; the order is fixed in the plan. **Clearing `personId` on archive loses the association an administrator wanted back.** **Mitigation:** archiving a person is itself reversible, and the audit row carries the previous value, so the link is recoverable from the trail. **The new route becomes an account-takeover path.** **Mitigation:** it is one of the seven places ADR-0104's stronger-user rule covers, for exactly this reason — rebinding an account to a different person changes who that account represents. |
| **Consequences** | A partial unique index on `users.personId`. A `check-person-id-duplicates` script run before it. `PATCH /users/:id/person`. `FederationPersonnelsService.remove` clears the link on archive. |
