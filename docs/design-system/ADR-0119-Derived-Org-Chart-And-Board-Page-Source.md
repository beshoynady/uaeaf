# ADR-0119 — The org chart is computed at read time, and the board page reads appointments

| Field | Details |
| --- | --- |
| **Status** | Accepted. Recorded 2026-09-26. Closes P0-1 in `docs/reviews/accounts-profiles-review.md`. |
| **Authority** | Product Owner brief, 2026-09-26 (decisions F1, F8, F10). |
| **Amends** | `board-members-screen.tsx` changes its data source. Adds public read endpoints for appointments by cycle, committees and their members, and a derived org chart. |
| **Does not amend** | **`organizationalStructure`** — the collection is not touched, not written and not read by the org chart (brief F10). · ADR-0102 §D2 page activation. · `currentLeadership`'s filtering, which is already correct and tested. |
| **Context** | The board page is wrong in a way that publishes real people's details under a false heading. It reads `GET /federation-personnel/public`, which returns **every** person whose `status` is `Active` — no filter on holding a post — and renders each as a board member, with the announced count taken from that list and a live `mailto:` for anyone with a recorded address. Any staff member, committee member or executive appears as a member of the board. Meanwhile the correct source already exists and is unused: `currentLeadership` filters to `President` and `BoardMember`, requires the appointment to be `Active` with an unexpired term, returns five fields, and is covered by nine tests — one of which is named for leaving committee roles out. Separately, the committees page cannot be built at all: there is no public committee list, only a per-id read, and no endpoint for a committee's members. |
| **Decision** | **The board page reads `GET /federation-appointments/public`**, the announced count is the number of serving post-holders, and a `mailto:` appears only when ADR-0117's switch is on. The public surface is completed: `GET /federation-appointments/public?electionCycleId=` (current cycle by default, an archive when a cycle is named), `GET /committees/public` with each committee's chair, `GET /committees/:id/members/public`, and `GET /federation-personnel/:slug/public`. **The org chart is derived at read time** from appointments, committees and club counts — `organizationalStructure` is left alone. Every one of these is built without N+1 queries. |
| **Alternatives Considered** | **(A) Filter `federation-personnel/public` down to people who hold a board post.** Rejected: it puts appointment logic in the personnel service, duplicating `currentLeadership`, and the page still would not have `positionTitle`, which lives on the appointment and is what a board card needs to print. **(B) Keep the personnel source and relabel the page.** Rejected: the page is the board's page by the approved IA; the heading is right and the data is wrong. **(C) Populate `organizationalStructure` from appointments and read the tree from it.** Rejected per the brief and on merit: it is a second source of truth for facts that already exist in `federationAppointments` and `committees`, kept in step by a synchronisation nobody would maintain — and the review already found that collection's public read is per-id only, with no way to fetch the tree. **(D) Build the chart client-side from the existing public endpoints.** Rejected: it would need the full committee and appointment lists on every visit, and the shape of the chart is a server concern that should not be re-derived by each client. |
| **Why This Decision** | The board fix is a change of source, not a new feature: the right endpoint exists, is filtered correctly, and is already tested — the page simply calls the wrong one. Deriving the org chart follows the same principle that rejected (C) for the board: the federation's structure **is** its appointments and committees, and a stored copy of a derived fact is a copy that goes stale. |
| **Risks** | **The derived chart is slower than reading a stored tree.** **Mitigation:** three queries with the ADR-0116 indexes, assembled in memory, and the public read is cached for 60 seconds — the same pattern `currentLeadership` already uses to avoid N+1. **Removing the personnel source hides someone the federation expected to see.** **Mitigation:** intended — they were never board members. The change is verified against the live record before and after. **A committee with no chair renders an empty card.** **Mitigation:** the chair is optional in the response and the card omits the line, the same discipline as the unringed portrait when a photo does not resolve. **The 60-second cache reads as "the save did not work".** **Mitigation:** verification confirms the API record first, then waits out the window and loads twice — the established procedure for this codebase. |
| **Consequences** | `board-members-screen.tsx` reads `/federation-appointments/public`. Four new public endpoints plus `GET /org-chart/public`. `currentLeadership` takes an optional `electionCycleId` and filters `roleType` in the query rather than in memory. `CommitteesService` gains a public list and a members read, both going through the publication snapshot since `committees` is workflow-governed. `organizationalStructure` is untouched. |
