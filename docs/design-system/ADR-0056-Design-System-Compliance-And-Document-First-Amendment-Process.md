# ADR-0056: Design System Compliance and the Document-First Amendment Process (Figma Visual Polish & FigJam Schema Transition)

| Field | Details |
| --- | --- |
| **Status** | Accepted |
| **Authority** | Project Owner Decision (Design System Governance) |
| **Context** | Real frontend implementation is starting against the 27-chapter Design System (Frozen v1.0) — `apps/web`/`apps/dashboard`/`packages/ui` per Chapter 21 §21.6. Two friction points surfaced at this transition, both already identified by the project owner rather than discovered here: (1) the current Figma UI designs are visually rigid/unpolished relative to the platform's intended quality bar, and requiring a full Figma redesign pass before any frontend code starts would block real build work indefinitely on a pass with no fixed scope yet; (2) the FigJam physical schema diagram needs field-level revision, collection by collection, to be genuinely production-ready — the same kind of gap ADR-0054 already found and fixed for Domain 5 Media Center specifically, but this time without a fixed, complete list of which of the ~84 collections are affected. Both are real, acknowledged gaps in an otherwise-frozen framework, not reasons to weaken it. This ADR formalizes how the framework stays authoritative while those two gaps are worked through. |
| **Decision** | **(1) Default compliance is mandatory, not optional.** Every future chapter, Figma design, or FigJam schema element remains binding as documented; nothing is skipped quietly because it is inconvenient. **(2) Document-first amendment process.** Any conflict between the Design System (or the FigJam schema) and an actual project need — or any case where an existing chapter, Figma design, or schema decision is judged wrong or no longer fit for purpose — is resolved by recording a formal, explicit amendment (a new ADR, or a documented amendment note referencing the ADR/chapter/schema element it changes) **before** the change is implemented in code, Figma, or FigJam. An existing documented decision is never silently overridden or routed around; if something is wrong, it is fixed for real, with a recorded reason. This applies symmetrically to all three governed artifacts: the 27 written chapters, the Figma UI implementing them, and the FigJam physical schema diagram. **(3) Figma visual polish — temporary code-first transition.** Frontend visual design (the polish/aesthetic-treatment layer only — not Chapter 21's architecture conventions, not Design Tokens, not IA/section ordering) will be iterated directly in code during the build rather than gated on a full Figma redesign pass. Figma is updated to match the finalized in-code visual treatment once a given section/page stabilizes. This is an explicit, temporary transition arrangement for this build phase, not a permanent reversal of Figma-leads-implementation. **(4) FigJam schema — incremental, build-order-driven review.** No large upfront re-audit of all ~84 collections is planned. Each collection is instead reviewed for production schema fitness immediately before the frontend section that depends on it is designed/built — the same pattern ADR-0054 already used for Media Center, now adopted as the platform's standing approach rather than a one-off. Any schema change found this way follows the §2 document-first rule: recorded at minimum as a dated note (or a full ADR where the owner/panel judges the change significant enough) before implementation, with the backend/FigJam updated to match before that section's frontend is built against it. |
| **Alternatives Considered** | (A) A full Figma redesign pass before any frontend code starts — rejected: no fixed scope exists for "significant improvement" yet, and the final visual form is expected to emerge through in-code iteration anyway, so a separate upfront pass would duplicate work and stall the build with no clear finish line. (B) A full upfront re-audit of all ~84 collections before frontend build begins — rejected: there is no fixed, complete list of needed changes today (explicitly out of scope for this session), and, as ADR-0054 already demonstrated for Media Center, most collections only reveal their real fitness gaps once a specific frontend section is actually built against them; a speculative full audit risks reshaping schema for sections that won't be built for a long time while adding no value to the sections actually next in the build order. (C) Allow undocumented, ad hoc deviations from the Design System when inconvenient, formalizing them later if at all — rejected: this is precisely the silent-override failure mode point (2) exists to prevent; it would erode the frozen baseline's authority and leave no trail for a future maintainer. |
| **Why This Decision** | Keeps the frozen Design System authoritative while honestly acknowledging that two specific areas of it — Figma visual polish and FigJam schema completeness — are not yet fully fit for production, rather than either freezing all frontend work until both are perfected or silently building around the gaps. The document-first rule continues this project's existing amendment discipline (already demonstrated in ADR-0054/ADR-0055's schema hardening and ADR-0041's narrowly-scoped micro-label exceptions) instead of adopting a weaker standard now that real implementation pressure has begun. |
| **Risks** | Figma temporarily lagging code for visual polish means Figma is, for a window of time, not the literal current source of truth for visual treatment on a given section. **Mitigation:** the exception is explicitly scoped to polish/visual-treatment only — Chapter 21 architecture, Design Tokens, and IA/section ordering (CLAUDE.md §11) remain governed by Figma/the chapters as before — and is explicitly temporary, closed out per section as Figma is updated to match. A future reader must not read this ADR as a permanent reversal of Figma's lead role. Incremental, build-order-driven schema review means collections late in the build order could carry undiscovered production-fitness gaps for a long time. **Mitigation:** the same explicit-tracking discipline ADR-0054 already established (`docs/audits/media-gallery-open-decisions.md`-style logging of deferred gaps) applies to whatever each per-section review finds. Allowing "a dated note" rather than a full ADR for less-significant schema changes is a lower documentation bar. **Mitigation:** the note-vs-ADR choice is explicitly left to owner/panel judgment per case, not automatic, so a change that turns out to matter more than first thought can still be escalated to a full ADR. |
| **Consequences** | Every future frontend build session must, by default: (a) treat the relevant Design System chapter(s) as binding compliance, (b) treat a visual-polish deviation as acceptable without a separate ADR only while it stays within the point-(3) scope (no Chapter 21/token/IA changes), and (c) run the point-(4) incremental schema-fitness check against FigJam for the collection(s) that section depends on, recording any resulting change per point (2) before implementing it. This generalizes the pattern ADR-0054 used once for Media Center into the platform's standing methodology for the remainder of the build. This ADR records the process only — it does not identify, list, or change any specific collection, field, or Figma frame; those will be recorded separately, as dated notes or their own ADRs, as each per-section review actually happens. |
