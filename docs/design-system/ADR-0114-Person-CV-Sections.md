# ADR-0114 — A person's record carries five CV sections, each item shown or hidden on its own

| Field | Details |
| --- | --- |
| **Status** | Accepted. Recorded 2026-09-26. Closes P1-4 in `docs/reviews/accounts-profiles-review.md`. |
| **Authority** | Product Owner brief, 2026-09-26 (decision F7), which resolves the spec's earlier question 3 in favour of embedded arrays. |
| **Amends** | `federationPersonnel` gains five arrays and a `slug`. |
| **Does not amend** | `federationAppointments` — posts held **inside** the federation stay there, and `previousPositions` covers outside roles only. · The `[RESTRICTED]` `internalContact` split. |
| **Context** | The person record holds `fullName`, a photo, `shortBio`, one `biography` field, nationality, contact and social links — nine fields. The approved plan is a personal page like a CV, with qualifications, certifications and courses, previous positions outside the federation, experience and achievements, each section controlling its own visibility. None of that exists, so the page cannot be built: one `LocalizedText` biography is not a set of repeatable, individually publishable entries. |
| **Decision** | Five arrays of subdocuments on `federationPersonnel`: `qualifications`, `certifications`, `previousPositions` (outside the federation only), `experience`, `achievements`. Every element carries `isVisible: boolean` and `displayOrder: number`, and all text is `LocalizedText`. The record also gains a `slug`, generated from the English name, editable, with a **partial unique index** on `archivedAt: null` — the `pages.slug` precedent. Visibility is **per item, not per section**. |
| **Alternatives Considered** | **(A) A separate `personCredentials` collection** keyed by `personId` with a `sectionType`. Cleaner for querying and paging, and rejected because nothing queries across people: every read is "this person's CV", which an embedded document answers in one read. Revisit if a requirement like "everyone holding an IAAF certificate" appears. **(B) Reuse the existing `ContentBlock`.** Cheapest, and rejected: the sections become free text, so the structure that makes an entry a *qualification* with a date and an institution is lost, and the query in (A) becomes impossible rather than merely unnecessary. **(C) Visibility per section rather than per item.** Rejected: a person may hold one certificate they would rather not publish while publishing the rest, and a section-level switch forces all-or-nothing. **(D) No `slug`, address the page by `ObjectId`.** Rejected: a public personal page with a 24-character hexadecimal URL is not shareable, and the platform already has the slug pattern. |
| **Why This Decision** | The five sections are always read together, in the context of one person, and never queried across people — which is exactly the shape an embedded array serves best and a separate collection serves at the cost of an extra read per page. Per-item visibility costs one boolean and removes the only scenario where the feature would be unusable. |
| **Risks** | **The document grows unbounded.** **Mitigation:** the realistic ceiling is tens of entries per person, far inside MongoDB's document limit; a person with hundreds is a signal to revisit (A), not a failure. **A slug collision on backfill.** **Mitigation:** the backfill script **reports** collisions rather than disambiguating them silently, so a human decides which person keeps the plain slug. **An invisible item leaks through a new endpoint.** **Mitigation:** the public read filters `isVisible` in the projection, and the public DTO is an allow-list, so a new field is not published by default. |
| **Consequences** | Five `@Prop` arrays plus `slug` on `federationPersonnel`, with a partial unique index. A `backfill-personnel-slug` script. `GET /federation-personnel/:slug/public` returns the profile with only visible items. The dashboard editor for these sections is **out of scope** for this work (brief §6) and arrives with the design update. |
