# ADR-0054: Media Gallery Hardening (Album / MediaAsset / MediaFile / ContentAssociation)

| Field | Details |
| --- | --- |
| **Status** | Accepted |
| **Authority** | Engineering Decision (Backend Architecture) |
| **Context** | Domain 5 — Media Center's `Album`, `MediaAsset`, `MediaFile`, and the shared `ContentAssociation` sub-schema were already implemented and working (associations-based linking, guarded publication-state transitions, partial-unique slug index) but were missing fields several already-implied CMS features need something to write to: per-album asset ordering (drag-and-drop), per-asset visibility/featured flags, a denormalized album asset count, storage-provider-independent file references, and a role/order concept on shared associations. This pass (2026-09-04) hardens the existing shape rather than rearchitecting it. |
| **Decision** | Added, additively, with no breaking changes to any existing field: **`ContentAssociation`** — `role` (enum `Primary`/`Featured`/`Related`, default `Related`) and `displayOrder` (default `0`). **`Album`** — `assetCount` (default `0`, denormalized, maintained by `MediaAssetsService`, not a source of truth) and an index on `{contentCategoryId, publicationState}`. **`MediaAsset`** — `displayOrder` (required), `isVisible` (default `true`), `isFeatured` (default `false`), and indexes on `{albumId, displayOrder}` and `{albumId, isVisible, displayOrder}`. **`MediaFile`** — `originalName` (required), `storageKey` (required, independent of `url`), `checksum` (nullable, not yet computed — see `docs/audits/media-gallery-open-decisions.md`). `MediaAsset.albumId` deliberately stays nullable (unassigned Media Library assets remain a supported state). `ContentAssociation.ownerType`'s existing camelCase collection-name convention (`championships`, `athletes`, `clubs`, `publicEvents`) was reaffirmed, not changed. |
| **Alternatives Considered** | (A) Recompute `Album.assetCount` via a scheduled job instead of maintaining it at write time — rejected: adds an infra dependency (a job scheduler) this codebase doesn't have yet, for a value only two write paths (`MediaAssetsService.create()`/`remove()`) currently affect. (B) Give `MediaAssetsService` a dependency on `AlbumsRepository` via `AlbumsModule` (either directly or via `forwardRef()`) to update `assetCount` — rejected: `AlbumsModule` already imports `MediaAssetsModule` (for `assertUsableImage()`), so this would create a circular module dependency; registering the `Album` model a second time in `MediaAssetsModule`'s own `MongooseModule.forFeature()` avoids the cycle entirely, since Mongoose reuses an already-compiled model for a given connection+name when the schema instance is reference-identical (`AlbumSchema` is a singleton import). (C) Follow `documents.ownerType`'s `PascalCase` convention (`'Championship'`, `'Club'`, ...) for any new `ContentAssociation.ownerType` values — rejected: that is a pre-existing, divergent naming convention on a *different* schema, not the platform's general rule; `ContentAssociation.ownerType` already correctly uses camelCase collection names, matching `workflowInstances`/`revisions`/`publications`, and this pass did not introduce a second casing convention alongside it. |
| **Why This Decision** | Every added field maps to a CMS capability the collections already implied but couldn't support (ordering, visibility, featured placement, asset counts, storage-migration-safe file references) — none is speculative. Keeping `assetCount` denormalized-but-write-path-maintained (rather than always-computed) matches this codebase's existing conventions elsewhere and avoids adding new infrastructure for a narrow need. Avoiding the circular module dependency via a second `forFeature()` registration is simpler and more standard in this codebase than introducing `forwardRef()`, which is used nowhere else in this project. |
| **Risks** | `MediaFile.checksum` exists but is always `null` today (nothing computes it) — a reader could mistake its presence for an active integrity-verification feature. **Mitigation:** the field's schema comment and `MediaFileDto`'s comment both state this explicitly, and it is tracked in `docs/audits/media-gallery-open-decisions.md` item 2. `Album.assetCount` will drift from the real count if a future code path modifies `MediaAsset.albumId` without going through `MediaAssetsService.create()`/`remove()` (e.g. a future "move asset between albums" endpoint) — **Mitigation:** documented directly in the `Album.assetCount` schema comment as a required consideration for that future path. |
| **Consequences** | `docs/audits/media-gallery-open-decisions.md` created, tracking four explicitly out-of-scope items (image derivatives, upload-time security validation, `photographerId`, EXIF/GPS policy) that are real gaps, not silently deferred. `videos.schemas.ts`/`VideosService` — the only other consumer of `ContentAssociation` — were updated to populate the new `role`/`displayOrder` fields identically, since the sub-schema is shared. No existing route, DTO field, or index was removed or renamed. |
