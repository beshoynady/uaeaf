# ADR-0118 — The editorial cycle is completed for every governed type, and person records join it

| Field | Details |
| --- | --- |
| **Status** | Accepted. Recorded 2026-09-26. **PENDING FIGMA BACK-SYNC.** Closes P1-6 in `docs/reviews/roles-permissions-review.md`. |
| **Authority** | Product Owner brief, 2026-09-26 (decision F9), which explicitly approves amending the closed entity-type list. |
| **Amends** | **FigJam domain note `100:7435`** — the closed List A / List B entity-type lists gain `federationPersonnel`. This is a deliberate amendment to an approved decision, not an oversight, and it is why this ADR exists rather than a code change alone. |
| **Does not amend** | The workflow engine itself (brief §8) — only type registration and the completion of routes that were always intended. · `federationAppointments`, which stays **outside** the workflow: an appointment is an administrative fact, and its protection is the audit trail, not an approval queue. · The 2026-09-20 separation of approval from publication. |
| **Context** | The roles review measured a gap nobody had noticed: the editorial cycle — `editorialState`, `submit`, `publishApproved`, `publishDirect`, `restore` — is wired for **five** entity types, while the approval-policy screen accepts **ten**. For `governanceDocuments`, `organizationalStructure`, `committees`, `documents` and `contactMessages` an administrator can switch approvals on and nothing can move: there is no submit route and no publish route, and four of the five have **no `Publish` permission in the catalogue at all**, so no role can ever hold it. `committees` is the clearest case — it is inside the closed List A and List B today, its schema comments say its public read goes through `publications → revisions.snapshotData`, and it cannot be published. Adding `federationPersonnel` naively would land it in exactly that state. |
| **Decision** | **First, complete the cycle for the types already governed:** each gains `Publish` in the capability map with a route to guard it, a `PUBLISH_REQUIREMENTS` row, and the five editorial routes. **Then** `federationPersonnel` joins `WORKFLOW_ENTITY_TYPES` **and** `PUBLICATION_ENTITY_TYPES`, with the same six elements, and its public read moves to `publications → revisions.snapshotData`. Its **default policy is direct publish**, so nothing changes operationally until the federation chooses otherwise. |
| **Alternatives Considered** | **(A) Add `federationPersonnel` to the list and stop there.** Rejected: it is the naive change, and `committees` is the standing proof of what it produces — a type that can be submitted and approved and never published. **(B) Complete the cycle for `federationPersonnel` only and leave the other five.** Rejected: it leaves the policy screen offering five settings that cannot work, and the next person to switch one on discovers it in production. **(C) Remove the five unfinished types from the governable list instead of completing them.** Cheaper, and rejected because `committees` is genuinely editorial content by its own schema's reasoning — the federation will want review on committee descriptions, and removing the option denies a requirement rather than deferring it. Offered as the fallback if the batch overruns. **(D) Default `federationPersonnel` to requiring approval.** Rejected: it changes how the federation works on the day of deploy, without anyone asking for it. Direct publish preserves today's behaviour and leaves the choice on the screen. **(E) Put `federationAppointments` in the workflow too.** Rejected per the brief: appointing a board member is a recorded administrative act, not editorial copy, and an approval queue in front of it adds ceremony without adding correctness. |
| **Why This Decision** | Type registration is one line and the capability it implies is six. The review's evidence is that the one-line version has already been done once, for `committees`, and produced a dead setting — so completing the cycle first is not thoroughness for its own sake, it is the difference between a working feature and a second dead one. The direct-publish default is what makes the change safe to deploy without a coordinated operational switch. |
| **Risks** | **`publications`/`revisions` need a shape change to carry a person record.** **This is the plan's named stop-and-ask point.** The snapshot is built server-side from the stored record, so no shape change is expected — but if one turns out to be needed, the work stops and the owner is asked, because that is the workflow core. **The public board and personnel pages break when the read path moves.** **Mitigation:** the source change (ADR-0119's board fix) lands first and is verified, and the read-path move is verified against a live publication before the old path is removed. **A person record with no Live publication becomes invisible.** **Mitigation:** the `PUBLISH_REQUIREMENTS` row plus a backfill that publishes existing active personnel, so the site does not empty on deploy. **The FigJam board and the code disagree.** **Mitigation:** recorded as **PENDING FIGMA BACK-SYNC** in this ADR's status, to be reconciled when Figma access is confirmed — never edited blind. |
| **Consequences** | Five entity types gain `Publish` plus the five editorial routes and a `PUBLISH_REQUIREMENTS` row. `federationPersonnel` joins both entity-type lists, gains `publicationState`, and its public read moves to the publication snapshot. Adding it to `PUBLICATION_ENTITY_TYPES` forces a `PUBLISH_REQUIREMENTS` entry **by compile error** — `Record<PublicationEntityType, …>` — which is a mechanical gate the plan relies on rather than a checklist item. A default policy row is seeded at direct publish. |
