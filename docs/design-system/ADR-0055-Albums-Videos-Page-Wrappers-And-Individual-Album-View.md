# ADR-0055: `albumsPage`/`videosPage` Hero Wrappers and the Individual Album Public View

| Field | Details |
| --- | --- |
| **Status** | Accepted |
| **Authority** | Engineering Decision (Backend Architecture) |
| **Context** | Follows ADR-0054 (media gallery hardening). Two gaps remained in Domain 5 — Media Center: (1) the Albums gallery and Videos listing sections had no Hero/management page, unlike every other public listing section (`athletesPage`, `clubsPage`, `newsPage`, ...), breaking consistency with the established ten-collection `HeroPageSchema` singleton pattern; (2) there was no public route to view a single album at all — not a missing filter on an existing controller, but a fully absent one (`AlbumsController` had zero `@Public()` routes before this session; verified in code, not assumed). |
| **Decision** | Added `albumsPage`/`videosPage` as pure `HeroPageSchema` wrappers with no additional fields, wired through the existing `SingletonPageService`/`*PageRepository`/`*PageController` pattern exactly like the other ten wrappers — confirmed via `athletesPage`'s own schema comment ("the same exemption class as `albums`") that none of the ten are workflow-governed (`WORKFLOW_ENTITY_TYPES`/`PUBLICATION_ENTITY_TYPES`), so `albumsPage`/`videosPage` follow that same self-published pattern, not the governed-editorial one used by `visionMissionPage`/`strategicPlansPage`. Added `GET /albums/public/:slug` (public, following `pages.controller.ts`/`athlete-profiles.controller.ts`'s route-ordering convention) returning the album's public-safe shape, its `isVisible` photos in `displayOrder`, and a related-albums strip (other `Published` albums sharing any `{ownerType, ownerId}` association target, capped at 8, sorted by `publishedAt` desc). No new collection was created for the individual album view — per the task's own explicit instruction and because the existing `albums`/`mediaAssets` collections (as hardened in ADR-0054) already carry every field the view needs (`slug`, `publicationState`, `isVisible`, `displayOrder`, `associations`). |
| **Alternatives Considered** | (A) A dedicated `albumDetailPage`/`albumViewPage` collection for the individual album view — rejected: there is no page-level configuration to store (no hero trio, no layout choice); the view is entirely derived from the requested album's own data plus a computed related-albums list, so a wrapper collection would hold nothing but be one more thing to keep in sync. (B) Rank related albums by number of shared association targets, or weight `Primary`-role targets higher — rejected for this pass: a flat "any shared target, newest-published-first, capped at 8" query is the correct scope per the task's own explicit instruction; relevance ranking is a genuine future enhancement, not built speculatively. |
| **Why This Decision** | Matches existing, already-established platform patterns in both halves of this change: the hero-wrapper singleton pattern for `albumsPage`/`videosPage` (identical to ten existing collections), and the `public/:slug` route + distinct public-response-DTO pattern for the album view (identical to `pages`/`athlete-profiles`). No new architectural pattern was introduced. |
| **Risks** | `AlbumPublicResponseDto.coverImageId` (and `RelatedAlbumSummaryDto.coverImageId`) are returned as plain ids, not resolved image URLs — consistent with how `heroImageId`/`photoId` already work platform-wide, but this means there is currently no public way to resolve any of these ids to a usable image URL at all (there is no public `GET /media-assets/:id`). This is a pre-existing, platform-wide gap, not introduced by this change — logged in `docs/audits/media-gallery-open-decisions.md` item 5's neighboring context, not treated as in-scope to fix here. The individual album page's own photo grid (`mediaAssets[]`) is unaffected — it embeds full resolved `file.url` data directly, since that data is the entire point of that specific list. |
| **Consequences** | `docs/audits/media-gallery-open-decisions.md` gained item 5: the `ContentAssociation.ownerType` (camelCase) vs. `documents.ownerType` (PascalCase) casing divergence, discovered while confirming the association-based related-albums query, logged rather than silently normalized. `HeroPageSchema`/`HeroPageDto`'s shared doc comments updated from "ten" to "twelve" wrapper collections. |
