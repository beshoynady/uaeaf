# ADR-0107 — An approval policy cannot change while content is under review, and every change is recorded

| Field | Details |
| --- | --- |
| **Status** | Accepted. Recorded 2026-09-26. Closes P1-1 and P1-2 in `docs/reviews/roles-permissions-review.md`. |
| **Authority** | Product Owner brief, 2026-09-26 (decision A7). |
| **Amends** | `ApprovalConfigurationService.disable` gains the running-reviews check that `configure`'s arrangement path already has. Policy writes gain their own audit row. |
| **Does not amend** | `assertNothingRunning`'s existing refusal on arrangement changes, or its reasoning. · `WorkflowPolicy`'s schema or its unique index. · The two-state policy model (requires approval / publishes directly). |
| **Context** | Two defects with one root. **Turning approvals off strands content.** `configure()` calls `assertNothingRunning` only when the *arrangement* changed; `disable()` has no such check. After disabling, an `InProgress` instance cannot be published by either path: `publishDirect` refuses because an active review exists, and `publishApproved` refuses because the policy now resolves to `direct` and tells the caller to publish directly — which the first refusal forbids. The content waits until someone thinks to cancel the review. **And the act that stranded it leaves no trace.** `configure` returns a `GovernableEntity`, which carries no `_id`, and its route's path parameter is `entityType`, not `id` — so both of the audit interceptor's identity sources are undefined and the row is skipped entirely. Turning the federation's approval requirement on or off, and changing who approves, is the most governance-sensitive write on the platform and it is invisible. The sibling route fares only slightly better: it is audited, but `previousValue` is null, so "this type stopped requiring approval" is not recoverable from the log — only its new state is. |
| **Decision** | **Lock:** both `configure` and `disable` refuse while any review is running under that entity type, and the refusal carries the pending list — entity ids, titles and current step — so an administrator can chase the reviewers or wait, rather than guess. **Log:** every policy change writes its own audit row, explicitly, inside the service, under `@SkipAuditLog()`, carrying the old and the new arrangement. |
| **Alternatives Considered** | **(A) Allow disabling and cancel the running reviews automatically.** Rejected: it destroys review records as a side effect of a settings change, and an approval already given disappears without the approver knowing. **(B) Allow disabling and let the stranded content through `publishDirect`** by relaxing its active-review refusal. Rejected: that refusal is what stops a direct publish racing a review, and removing it to fix a settings problem trades a stuck record for a wrong one. **(C) Migrate the running reviews to the new arrangement.** Rejected for the reason already recorded on `assertNothingRunning`: there is no reading of a half-migrated approval that is safe to publish from. **(D) Fix the audit gap by returning the policy's `_id` in the response.** Rejected as the primary fix — it works, but it leaves the audit row's shape at the mercy of a response DTO, and `previousValue` would still be null because the interceptor's pre-read also needs a path `:id`. An explicit write in the service says what changed, both sides, on purpose. **(E) Fix only the interceptor and rely on it here.** Rejected: ADR-0112 does fix the interceptor's silent skip, and this route would then log a row with `entityId: null` — better than nothing, and still not the old value. |
| **Why This Decision** | A policy is configuration that governs records already in flight, so the safe moment to change it is when nothing is in flight — the same conclusion `assertNothingRunning` already reached for the arrangement, applied to the on/off switch that was overlooked. And the logging is written explicitly rather than inferred because this is the one write where a generic mechanism has no id to find: naming the change in the service is both more honest and more complete than teaching the interceptor to guess. |
| **Risks** | **An administrator cannot turn approvals off during a genuine emergency** because one review is open. **Mitigation:** the refusal names the exact items, and cancelling a review is one action away with `workflowInstances:Update` — a deliberate, audited step rather than a silent side effect. **The pending list is expensive to compute on a settings screen.** **Mitigation:** the count is already computed for `GovernableEntity.inFlightReviews`; this returns the rows behind the number that is already there. **The explicit audit write is forgotten on a future policy route.** **Mitigation:** ADR-0112's route-coverage test fails any mutating route without an identity source, so a new policy route cannot land silently. |
| **Consequences** | `ApprovalConfigurationService.disable` calls `assertNothingRunning`. Both write methods write an audit row with old and new values and are marked `@SkipAuditLog()`. The refusal payload gains the pending list. `workflow-policies.controller.ts` write routes gain step-up (ADR-0108). The policy screen shows pending content and blocked assignees (ADR-0106). |

## D1 — Why the refusal carries the list, not just a count

`inFlightReviews` already tells an administrator *how many*. It does not tell them
whether to wait ten minutes or telephone somebody, which is the only decision they
are actually making at that moment.

So the refusal returns the entity ids, their titles and the step each is sitting
on. This is the same reasoning `assertNothingRunning` recorded for putting the
count in the payload — extended one step, because a number without names still
leaves the administrator with nothing to do.
