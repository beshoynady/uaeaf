## Deviations from the approved plan

- Item 5: fixing `clubs`/`coaches.registrationNumber` uniqueness required wrapping the whole `create()` call in a try/catch (the same shape as the `athleteProfiles` pattern), which as a natural side effect also gives `clubs`/`coaches.slug` proper `ConflictException` handling for the first time (previously an uncaught raw MongoDB driver error). Not a separate scope decision — the try/catch has to wrap the entire `repository.create()` call, it can't be scoped to one field's error only.
- Item 8: the approved plan named `@nestjs/throttler` but explicitly allowed flagging and substituting if it didn't fit. `npm view @nestjs/throttler version peerDependencies` and `npm view @nestjs/throttler versions --json` confirmed the latest published version (6.5.0) caps `@nestjs/common`/`@nestjs/core` support at `^11.0.0`; this project is on `^12.0.1`, and no published version supports NestJS 12. This was surfaced via an interactive question (three options: custom guard [recommended], force-install with `--legacy-peer-deps`, skip for now); the question was interrupted before an explicit choice was recorded, and the only follow-up was an instruction to continue. Proceeded with the previously-stated recommended option — a small custom in-house guard — since it was the lowest-risk path (no untested framework/NestJS-version combination) and no alternative preference was given.
- Item 8 testing: the first version of the rate-limit e2e coverage put both routes' checks in one file, sequentially bootstrapping two full `AppModule` instances against one shared `MongoMemoryServer`. That produced a `MongoNetworkError: ECONNRESET` partway through the run and a 60s test timeout. Split into two files — `rate-limit-contact-messages.e2e-spec.ts` and `rate-limit-login.e2e-spec.ts` — each with its own isolated `MongoMemoryServer` and single app instance, matching the one-app-per-file pattern already used by every other e2e spec in the suite. Both pass reliably (~12s combined) after the split.

## Item log

1. **P0 — AuditLogsRepository tamper-resistance.** Stopped extending `BaseRepository`; now exposes only `create()`. Verified no other file called the inherited `updateById`/`softDelete`. New test asserts the public surface has no mutation method. Commit `1681d2c`.
2. **P1 — auditLogs.entityType casing.** Added `kebabToCamel()` util (verified against all 62 controller routes) and wired it into `AuditLogInterceptor`. Historical rows are NOT backfilled. Commit `d8e9c96`.
3. **P1 — auditLogs + notifications indexes.** Added `{entityType,entityId,timestamp}` + `{actorId,timestamp}` on `auditLogs`, `{recipientId,readState,timestamp}` on `notifications`. Verified against real built indexes in new repository specs. Commit `e1fe4c5`.
4. **P1 — users.email normalization.** Added `lowercase`/`trim`; normalized `UsersRepository.findByEmail()`'s query input to match (Mongoose setters don't apply to raw query filters). Commit `c0c912e`.
5. **P1 — clubs/coaches.registrationNumber uniqueness.** Added `unique`/`trim` + duplicate-key → `ConflictException` via the existing shared `mongo-errors.util.ts`. Commit `7482a2c`.
6. **P1 — partial unique indexes, cross-schema.** Converted every `unique: true` index in the codebase to a partial index scoped to `{archivedAt: null}` across 9 schema files (`users`, `clubs`, `coaches`, `disciplines`, `athleteProfiles`, `officialProfiles`, `albums`, `pages`, `navigationMenus`). Representative (a)/(b)/(c) behavior verified against real MongoDB. Full suite (42 suites / 194 tests) passing. Commit `49419d5`.
7. **P1 — contactMessages input hardening.** Added `@MaxLength()` to every free-text DTO field (`senderName` 200, `senderEmail` 254, `senderPhone` 30, `messageBody` 5000, `replyBody` 5000) and a global 1MB request-body cap (`express.json`/`urlencoded` limits in `main.ts`, ahead of all routes — not scoped to this one controller, since Express body parsing happens before routing). Verified with two new e2e assertions: an over-limit `senderName` and an over-limit `messageBody` are each rejected with 400. Commit `13a8388`.
8. **P1 — Rate limiting.** `@nestjs/throttler` doesn't support this project's NestJS 12 — see the deviation note above. Built a custom `RateLimitGuard` (fixed-window in-memory counter keyed by `<ControllerClass>.<handler>:<ip>`, lazy expiry-on-access) plus a `@RateLimit(limit, windowSeconds)` decorator, registered `RateLimitGuard` first in the `APP_GUARD` chain — ahead of `JwtAuthGuard`/`PermissionsGuard` — so abusive traffic is rejected before any JWT verification work. Applied `@RateLimit(5, 60)` to `POST /contact-messages` and `@RateLimit(10, 60)` to `POST /auth/login`; the login limit is explicitly documented in `auth.controller.ts` as complementary to, not a replacement for, the existing per-account lockout (`LOCKOUT_THRESHOLD`/`LOCKOUT_DURATION_MINUTES` in `config/auth.config.ts`), which protects one account from repeated guessing while this protects the endpoint from distributed traffic across many accounts. The guard's in-memory, single-process-only nature is documented in its own TSDoc as an accepted tradeoff (would need a shared store such as Redis before running more than one API instance). 7 new unit tests (`rate-limit.guard.spec.ts`) plus 2 new e2e tests (one per rate-limited route, each confirming a 429 past the threshold) all passing; confirmed `login-lockout.e2e-spec.ts`'s 6 login requests stay safely under the new 10/60s login limit. Commit `1c59aed`.

Baseline was 36 suites / 174 tests; after all 8 items, the full suite is 43 suites / 201 tests (unit) + 7 suites / 7 tests (e2e), all passing, with a clean `nest build`.
